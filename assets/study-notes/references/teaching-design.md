# 教学设计规范（怎么教）

`notes-standard.md` 管"长什么样"，本文管"怎么教会"。写第一节之前读完；样章确认（P2.5）时，用户的反馈会覆盖本文里的默认值，写进 `checklist.md` 的风格约定。

<b>示例的适用范围</b>：本文里的示例（`project/`、minigrad、【新建】/【修改】标签、文件树等）取自代码类、计算机类、AI 类课程，专供这类任务参考。其他科目只要满足本文与 `notes-standard.md`的其他条款，步骤怎么切、产物长什么样、例子怎么选都有自由空间，按 `subject-playbooks.md` 里对应科目的打法来，不必向这些示例靠拢。

---

## 一、总原则

三条结构原则，决定一节长什么样：

- **A. 每件产物都是一条线。** 一章、一节、一步都有起点（读者手上已有的东西）和终点（多出来的东西）。读者任何时候都能说出"我现在在哪、下一步干什么"。
- **B. 每节都在长一份累积的、可检验的、可修改的东西。** 代码类是 `project/`；数学是推导本；语言是句子本；人文是时间线或论证稿。这一节在上一节的基础上改，下一节在这一节的基础上改。读者能自己验证它对不对（跑、算、默写、对照）。
- **C. 概念是节点，不是骨架。** 概念在第一次需要它的那一步被命名和讲清；节的组织单位是步骤，不是概念。

五条教法原则，决定每一段怎么写：

1. **先动手，后命名**：先让读者做一步、看到结果（常常是一个报错），再告诉他这叫什么、为什么。
2. **让读者动脑，而不是只看**：关键处先让读者猜、让读者补一步、让读者自己做。被动阅读的"懂了"最不可靠。
3. **每节都可检验**：导读里写的学习目标，练习里都要能考到；本节产物，读者自己能验证。
4. **克制**：篇幅、标注块、图都有预算。重点太多就等于没有重点。
5. **前后连贯**：后面的章节主动回顾前面的知识（间隔复习），而不是讲完就丢。

## 二、顺序感五机制

读者觉得"能从上读到下"，靠的是下面五个固定位置的句子。缺一个，读者就会在那里迷路。校验器按 [R1][R2][R5] 检查它们是否存在；写得好不好要靠顺读测试（第十二节）。

| # | 机制 | 位置 | 回答读者的哪个问题 |
|---|---|---|---|
| 1 | <b>承接块</b> | `## 接上一节`：<b>上一节做到</b> / <b>留下的坑</b> / <b>本节补上</b> | 我为什么要读这一节？ |
| 2 | <b>两行导读</b> | 导读里的 <b>你现在手上</b> / <b>本节结束时</b> | 我从哪出发、到哪结束？ |
| 3 | <b>动词步骤</b> | `## 第 N 步：<动词短语>`，每步「动作 → 可见结果 → 为什么」 | 现在该干什么？干完怎么知道对了？ |
| 4 | <b>坏掉时刻</b> | 至少一步里，读者真的撞上报错、失败的测试、反例或说不通的句子 | 为什么不能用更简单的办法？ |
| 5 | <b>钩子</b> | 节末 <b>留给下一节</b>；章末的通跑与项目地图 | 下一节动哪里？这一章我到底做出了什么？ |

写法要点：

- 承接块里的「留下的坑」要具体：一个读者已经能感受到的问题（"估一个导数要算两遍 f，一百万个参数就是两百万遍"），不是"本节将介绍 X"。
- 步骤标题连起来读应该是一串动作：「建出能 import 的空包 → 用差商估一个导数 → 把核对写成一条测试」。如果连起来是一串名词（「包 → 数值导数 → 单元测试」），这一节还是百科。
- 坏掉时刻用真实结果：真的跑出来的报错、真的算出来的反例。不要写"如果这样做就会出错"而不给出错的样子。
- 钩子指向一个具体的文件或动作（"下一节在 `project/minigrad/` 里新建 `value.py`"），不是"下一节我们将学习……"。

## 三、学习目标与练习对应

- 导读里写 **2–4 条学习目标**，用可检验的动词："能手算……""能解释为什么……""能写出……""能区分……和……"。不要写"理解""掌握"这类无法检验的词。
- 每条学习目标至少对应一道本节练习。写完练习后自查：有没有目标没被考到？有没有练习考的是导读里没提的东西？
- 可以在练习题号后标注对应目标，如 `**3.**（目标 2）`，不强制。

## 四、概念：就地出现

概念在第一次需要它的那一步里，以 `### 概念 N：名称` 短条目出现。它的四件事都是在那个位置、对着读者刚做的那件事讲的：

| 元素 | 必备？ | 就地怎么写 |
|---|---|---|
| 一句话 | 必备 | 对着刚才那一步说：「刚才那个斜率，就叫数值导数」 |
| 准确定义 | 必备 | `Note` + `<术语> 的定义`；数学类把量词、条件写全 |
| 一个例子 | 必备 | 优先用读者刚做出来的东西当例子；手算、算例、史料都行 |
| 一条易错点或辨析 | 必备 | `Warning` 标注块；最好是读者马上就会踩的那个坑 |
| 直觉 / 比喻 / 形式化 / 先猜一猜 | 按需 | 不要为凑骨架硬写 |

其他规则：

- 小节标题就是概念的名字：写 `### 概念 1：数值导数`，不写 `### 概念 1：关于导数的一些说明`。
- 概念条目短：通常 15–40 行。讲完就回到施工线上，下一行就是动作。
- 不要两个概念连排。一步里最多一个概念；第二个概念放到下一步，等读者需要它的时候。
- **不是所有知识点都要编号**。脱离上下文就失去意义的内容（某个参数、某行代码的作用、证明的中间步骤）留在「为什么」里讲，不编号、不进概念索引。
- 一节通常 1–3 个概念条目。超过 4 个说明这一节在讲概念而不是在做事，考虑拆节。
- 老库迁移期可以保留 `## 概念 N：名称`，但必须夹在两步之间（`notes-standard.md` 6.1）。

## 五、篇幅按学时算

预算的单位是读者的时间，不是行数：

| 项 | 默认预算 | 校验器 |
|---|---|---|
| 每节步骤数 | 3–5 步 | [R1] 少于 3 或多于 5 |
| 每一步 | 10–20 分钟（读 + 敲 + 跑 + 想） | 不检查 |
| 每节预计用时 | 30–100 分钟，写在导读 `预计用时 N 分钟` | [R10] 超出范围 |
| 每节总行数 | 通常落在 200–700 行；这是结果，不是目标 | 超过 800 行警告 |
| 每个【新建】文件 | ≤ 120 行 | [R4] |
| 每节标注块 | ≤ 20 个 | 超过 20 个警告 |
| 每节练习 | 3–5 题 | 少于 3 或多于 5 警告；`notes_data.js` 里报错 |
| 本节小结要点 | 5–8 条 | 不检查 |
| 本章速查 | 80–200 行 | 不检查 |

超了怎么办：<b>拆节</b>。一节要 6 步，就拆成两节，各 3 步，前一节的钩子就是后一节的承接。不要靠删掉「为什么」、合并步骤或"决定不拆"来硬塞。【新建】超过 120 行，就先新建骨架，再在后面几步里逐段【修改】。

标注块的使用原则：

- 标注块用来**打断阅读、提醒重点**。如果一段话不需要读者停下来，就写成普通正文。
- 不要连续堆叠两个以上标注块；不要用标注块包裹整段讲解。
- 每个概念条目通常只需要：1 个定义块 + 0–1 个易错块。

## 六、先猜后看（predict first）

在读者"以为自己懂了"的地方，先让他预测，再揭晓。适用场景：

- 代码运行结果（尤其是反直觉的：广播形状、浮点误差、引用 vs 拷贝、梯度累加）；
- 一个算例的结果、一个参数变化后的趋势；
- 一个常见说法是对是错。

写法：

```markdown
> <b>*Tip*</b>
> 先猜一猜
>
> 这一行会打印 `6.0` 吗？先写下你的答案，再运行。

【运行】在 `project/` 里：
（命令块）

<!-- output: code/out/c1s1-2.txt -->
（真实输出块）

<b>为什么不是 6.0</b>：……如果你猜的是 6.0，问题出在……
```

- 揭晓之后一定要解释"猜错的人通常错在哪"，这才是价值所在。
- 每节 1–3 处即可，放在最关键的地方。
- 代码类科目揭晓的输出必须是绑定的真实输出。**先跑，再写揭晓的解释**：真实结果常常和你预想的不一样，那正是最好的教学素材。

## 七、渐进练习（worked example → faded → independent）

一个新技能按三步交给读者：

1. **完整示范**：在某一步里把一件事从头到尾做一遍，每步写出依据。
2. **留空示范**：紧接着给一道同类题，关键的一两步留空让读者补（写成 `______` 或"你来写这一行"），答案紧跟在后面的标注块里（标题不要叫「答案与解析」，那是本节练习专用的）。不计入本节练习数。
3. **独立练习**：本节练习里出同类但换了情境的题，不给步骤提示。

本节练习 3–5 题，按难度递进：

| 位置 | 类型 | 作用 |
|---|---|---|
| 第 1 题 | 基础 | 直接检验定义或单步操作 |
| 第 2 题 | 应用 | 换个情境用一次 |
| 第 3 题 | 易错/辨析 | 针对本节最常见的误解，最好就是本节「坏掉时刻」那个坑 |
| 第 4–5 题（可选） | 综合/拓展 | 串起本节多个步骤，或连接前面章节 |

内容多、目标多的节出 4–5 题；内容少的节 3 题就够。每题至少对应一条学习目标。

## 八、间隔复习（spaced review）

讲完就丢的知识会很快遗忘。用四个地方把旧知识拉回来：

1. **承接块**：「上一节做到」就是一次最短的回顾。
2. **节导读的前置**：写明本节依赖前面哪几节，并给链接（跨章用 `../Cha_X …/`）。
3. **正文里的回顾**：用到前面章节的知识时，用一两句话复述要点并给链接，不要假设读者还记得。代码类科目里，改旧文件本身就是回顾：【修改】的上下文行让读者重新看到上一章写的东西。
4. **章末测试的回顾题**：从第 3 章起，每章测试含 10–20 分跨章回顾题，题号后标 `【回顾 CX】`。优先考"本章会用到的旧知识"，其次考前面章节的高频易错点。回顾题要覆盖至少两个不同的旧章节（第 3 章只能回顾第 1、2 章）。

## 九、本章速查

每章（毕业设计章除外）写一页 `CX 速查.md`，模板见 `templates/cheat-sheet.md`：

- 内容：核心定义一句话版、公式、API/命令表、"什么时候用哪个"对照表、本章 Top 易错点。
- 每条链回正文对应锚点。
- 不写新知识、不写长解释、不放练习。速查是检索用的，正课顺着读。
- 写完速查后对照它检查章末测试：速查里的每一块是否都被测试覆盖到了？

---

## 十、例子与比喻

- **例子要完整**：有输入有输出、有问题有结局，数据自洽。
- **反例和"看起来对但其实错"的版本最有价值**：每节至少一处，通常就是坏掉时刻。
- **比喻全库统一一套**（在 `checklist.md` 风格约定里写明），不要每节换。比喻负责直觉，定义负责严谨，两者都要有，不要用比喻代替定义。

## 十一、代码类科目：代码的出生地

读者手里的代码只有一个来源：他自己照正文在 `project/` 里敲出来的。由此有五条要求（R4–R8）。

<b>R4 · 代码有出生地</b>

- `project/` 从空目录开始。第 1 章第 1 节的第 1 步就让读者新建第一个文件。
- 每个代码块带标签：【新建】（整份文件，≤ 120 行）、【修改】（```diff 定位式改动，上下各 1–2 行原样上下文）、【重构】（整个函数或类换掉，并写清为什么）、【收口】（此刻整份文件应有的样子）。格式见 `notes-standard.md` 5.4。
- 不许节选，不许 `# ...` 省略，不许先展示最终版的类再说"我们一点点实现它"。读者此刻看到的版本，就是他此刻文件里应有的版本。
- `code/answer/chNN/` 是第 N 章做完时 `project/` 的样子，与 `project/` 同构。正文只在章末提它，用来对答案；不许引用晚于本章的答案。
- 读者不在 `code/` 里写东西：不要出现 `mkdir code/…`、`cd code/…`、【新建】`code/…`。

<b>R5 · 两行导读与坏掉时刻</b>：导读写 <b>你现在手上</b> / <b>本节结束时</b>；每节至少一次真实的报错或失败，然后修好它。

<b>R6 · 每节可运行，每章能通跑</b>：每一步结束时 `project/` 都能跑（至少 `python check.py` 不崩，或者崩在正文预告的地方）。每章最后一节有「章末通跑」：一条命令从头跑完整个 `project/`（通常是全部测试），带真实输出。

<b>R7 · 项目地图</b>：每章最后一节有「本章项目地图」：文件树 + 每个文件一句话职责 + 本章动了哪些文件。读者靠它确认自己的 `project/` 没有走岔。非代码科目写推导本、句子本等产物的目录，不要求 `project/`。

<b>R8 · notebook 只做演示</b>：想让读者"玩一玩"某个现象（步长对误差的影响、广播的形状），用 `code/notebooks/CN_主题.ipynb`：一格一件事、交付时不带输出、不写框架代码（框架代码只在 `project/`）。正文用 `<b>动手</b>：` 引用它，不需要输出绑定。

生成真实输出的做法：

1. 写完一节，跑 `node <skill>/scripts/run-course.mjs "<根>" --write`。它从空目录照正文重放，在每个【运行】时的快照里真实执行命令，把结果写进 `code/out/` 和正文的输出块，并生成 `code/answer/chNN/`。
2. 读一遍生成的输出。和你预想的不一样时，改正文的解释（或改代码），不要手改输出。
3. 跑 `check-library.mjs --strict`，确认重放、同构、标签都通过。

其他：

- 给一个"能跑但结果错"的版本并解释错在哪（往往就是坏掉时刻）。
- 代码类练习给出测试用例与期望输出，方便自评。

## 十二、顺读测试（操作定义）

顺读测试回答一个问题：<b>只靠正文，读者能不能从上读到下把东西做出来？</b>

<b>做法</b>：

1. 挑一章（样章阶段就是第 1 章第 1 节）。准备一个空的 `project/`（非代码科目是一张白纸或空的推导本）。代码类科目从上一章的 `code/answer/` 复制出 `project/` 作为起点。
2. 从该章第一节的导读开始，按出现顺序读。只做正文字面上叫你做的事：新建、修改、运行、写下、默写。
3. 不看 `code/`（章末对答案那一步除外），不跳读，不凭自己的经验补上正文没写的步骤，不调整顺序。
4. 每遇到一个结果（真实输出、`你应该看到`、算例的数），就和自己做出来的比。

<b>通过条件</b>（全部满足）：

- 每一步都能做下去：没有出现"这个文件在哪""这一行加在哪""这个变量哪来的"。
- 每一个结果都和正文一致；不一致的地方正文事先预告过（坏掉时刻）。
- 每节结束时，手上的东西和导读的 <b>本节结束时</b> 一致。
- 章末通跑通过，`project/` 与项目地图、`code/answer/chNN/` 一致。

<b>记录</b>：卡住的位置写进 `checklist.md`（文件 + 行号 + 卡在哪），修完再测。`run-course.mjs` 是它的机器版：能证明"照标签做得出来、输出是真的"；人工版补上机器查不了的部分：读者是否知道下一步该做什么、为什么。

## 十三、样章自查清单（P2.5）

把样章发给用户之前自查：

- [ ] 第一句告诉读者去哪敲什么（两行导读 + 承接块）
- [ ] 3–5 步，步骤标题连起来是一串动作；每步有动作、真实结果、为什么
- [ ] 至少一次坏掉时刻；至少一处先猜后看
- [ ] 概念以 `### 概念 N：名称` 出现在第一次用到它的那一步，没有连排
- [ ] 代码块都有标签，没有节选和省略；输出都是 `run-course.mjs` 跑出来的
- [ ] 导读的学习目标可检验，且每条都有练习对应；练习 3–5 题，每题后紧跟答案与解析
- [ ] 预计用时 30–100 分钟，标注块 ≤ 20
- [ ] 节末有「留给下一节」
- [ ] `check-library.mjs --strict --only` 0 error；自己做过一遍顺读测试
