# 教学设计规范（怎么教）

`notes-standard.md` 管"长什么样"，本文管"怎么教会"。写第一节之前读完；样章确认（P2.5）时，用户的反馈会覆盖本文里的默认值，写进 `checklist.md` 的风格约定。

---

## 一、总原则

1. **先问题，后定义**：每个新东西先回答"它解决什么问题、没有它会怎样"，再给定义、例子，最后才是形式化。
2. **让读者动脑，而不是只看**：关键处先让读者猜、让读者补一步、让读者自己做。被动阅读的"懂了"最不可靠。
3. **每节都可检验**：导读里写的学习目标，练习里都要能考到。
4. **克制**：篇幅、标注块、图都有预算。重点太多就等于没有重点。
5. **前后连贯**：后面的章节主动回顾前面的知识（间隔复习），而不是讲完就丢。

---

## 二、学习目标与练习对应

- 导读里写 **2–4 条学习目标**，用可检验的动词："能手算……""能解释为什么……""能写出……""能区分……和……"。不要写"理解""掌握"这类无法检验的词。
- 每条学习目标至少对应一道本节练习。写完练习后自查：有没有目标没被考到？有没有练习考的是导读里没提的东西？
- 可以在练习题号后标注对应目标，如 `**3.**（目标 2）`，不强制。

---

## 三、概念小节：必备与可选

概念以 `## 概念 N：名称` 就地展开。**不要求每个概念都走同一套六步骨架**——简单概念三段就够，复杂概念再展开。

| 元素 | 必备？ | 写法 |
|---|---|---|
| 一句话说明 | 必备 | 小节开头一两句话说清它是干什么的（正文或 `Note` 标注块都行） |
| 准确定义 | 必备 | `Note` + `<术语> 的定义`；数学类把量词、条件写全 |
| 具体例子 | 必备，至少一个 | 能算的给算例，能跑的给代码，人文类给史料或情境 |
| 易错点或辨析 | 必备，至少一条 | `Warning` 标注块，或"容易混淆 / 区别"对照表 |
| 为什么需要它 / 直觉 | 推荐 | 正文叙述，可配比喻；比喻用全库统一的那一套 |
| 形式化 | 按需 | 公式、伪代码、类型签名 |
| 先猜一猜 | 按需 | 见第五节 |
| 记住这些 | 按需 | 只在概念确实有 3 条以上需要记的要点时写 |

其他规则：

- 小节标题就是概念的名字：写 `## 概念 1：张量 Tensor 与 ndarray`，不写 `## 概念 1：关于张量的一些说明`。
- 概念小节内部用 `###` 分段，标题按内容取名（如「为什么需要它」「手算一遍」），不必固定。
- **不是所有知识点都要编号**。脱离上下文就失去意义的内容（证明的中间步骤、某段代码的上下文）留在正文叙述里，不编号、不进概念索引。
- 一节建议 2–5 个概念小节。超过 6 个说明这一节太大，考虑拆节。

---

## 四、篇幅与标注块预算

| 项 | 默认预算 | 校验器 |
|---|---|---|
| 每节总行数 | 300–800 行 | 超过 800 行警告 |
| 每节标注块 | ≤ 20 个 | 超过 20 个警告 |
| 每个概念小节 | 40–150 行 | 不检查 |
| 每节练习 | 3–5 题 | 少于 3 或多于 5 警告；`notes_data.js` 里报错 |
| 本节小结要点 | 5–8 条 | 不检查 |
| 本章速查 | 80–200 行 | 不检查 |

标注块的使用原则：

- 标注块用来**打断阅读、提醒重点**。如果一段话不需要读者停下来，就写成普通正文。
- 不要连续堆叠两个以上标注块；不要用标注块包裹整段讲解。
- 每个概念小节通常只需要：1 个定义块 + 0–1 个易错块 + 0–1 个先猜/想一想块。

篇幅超了怎么办：先删重复解释和不服务于目标的旁支；仍然超，就把推导细节移到节末「补充：……」小节，或拆成两节。

---

## 五、先猜后看（predict first）

在读者"以为自己懂了"的地方，先让他预测，再揭晓。适用场景：

- 代码运行结果（尤其是反直觉的：广播形状、浮点误差、引用 vs 拷贝）；
- 一个算例的结果、一个参数变化后的趋势；
- 一个常见说法是对是错。

写法：

```markdown
> <b>*Tip*</b>
> 先猜一猜
>
> `a + b` 的形状是什么？先在心里写下答案，再往下看。

<!-- output: code/out/ch1_broadcast.txt -->
```text
(3, 4)
```

结果是 `(3, 4)`。如果你猜的是……，问题出在……
```

- 揭晓之后一定要解释"猜错的人通常错在哪"，这才是价值所在。
- 每节 1–3 处即可，放在最关键的地方。
- 代码类科目揭晓的输出必须是绑定的真实输出。

---

## 六、渐进练习（worked example → faded → independent）

一个新技能按三步交给读者：

1. **完整例题**：正文里把一道题从头到尾做一遍，每步写出依据。
2. **留空例题**：紧接着给一道同类题，关键的一两步留空让读者补（写成 `______` 或"你来写这一行"），答案紧跟在后面的「答案与解析」块里。不计入本节练习数。
3. **独立练习**：本节练习里出同类但换了情境的题，不给步骤提示。

本节练习 3–5 题，按难度递进：

| 位置 | 类型 | 作用 |
|---|---|---|
| 第 1 题 | 基础 | 直接检验定义或单步操作 |
| 第 2 题 | 应用 | 换个情境用一次 |
| 第 3 题 | 易错/辨析 | 针对本节最常见的误解 |
| 第 4–5 题（可选） | 综合/拓展 | 串起本节多个概念，或连接前面章节 |

内容多、目标多的节出 4–5 题；内容少的节 3 题就够。每题至少对应一条学习目标。

---

## 七、间隔复习（spaced review）

讲完就丢的知识会很快遗忘。用三个地方把旧知识拉回来：

1. **节导读的前置**：写明本节依赖前面哪几节，并给链接（跨章用 `../Cha_X …/`）。
2. **正文里的回顾**：用到前面章节的知识时，用一两句话复述要点并给链接，不要假设读者还记得。
3. **章末测试的回顾题**：从第 3 章起，每章测试含 10–20 分跨章回顾题，题号后标 `【回顾 CX】`。优先考"本章会用到的旧知识"，其次考前面章节的高频易错点。回顾题要覆盖至少两个不同的旧章节（第 3 章只能回顾第 1、2 章）。

---

## 八、本章速查

每章（毕业设计章除外）写一页 `CX 速查.md`，模板见 `templates/cheat-sheet.md`：

- 内容：核心定义一句话版、公式、API/命令表、"什么时候用哪个"对照表、本章 Top 易错点。
- 每条链回正文对应锚点。
- 不写新知识、不写长解释、不放练习。
- 写完速查后对照它检查章末测试：速查里的每一块是否都被测试覆盖到了？

---

## 九、例子与比喻

- **例子要完整**：有输入有输出、有问题有结局，数据自洽。
- **反例和"看起来对但其实错"的版本最有价值**：每节至少一处。
- **比喻全库统一一套**（在 `checklist.md` 风格约定里写明），不要每节换。比喻负责直觉，定义负责严谨，两者都要有，不要用比喻代替定义。

---

## 十、代码类科目的额外要求

- 正文里的代码片段从 `<根>/code/` 里的真实文件摘取，片段前写 `<!-- source: … -->`；运行输出保存到文件，输出前写 `<!-- output: … -->`。格式见 `notes-standard.md` 5.4。
- 先给最小可运行版本，再逐步加功能；每一步都能跑。
- 给一个"能跑但结果错"的版本并解释错在哪。
- 代码类练习给出测试用例与期望输出，方便自评。

---

## 十一、样章自查清单（P2.5）

把样章发给用户之前自查：

- [ ] 导读的学习目标可检验，且每条都有练习对应
- [ ] 每个概念小节都有一句话、定义、例子、易错/辨析
- [ ] 至少一处先猜后看；至少一处完整例题 + 留空例题
- [ ] 练习 3–5 题，难度递进，每题后紧跟答案与解析
- [ ] 行数 ≤ 800，标注块 ≤ 20
- [ ] 代码与输出都绑定了真实文件（代码类科目）
- [ ] `check-library.mjs --only` 0 error
